Dispatcher определяет, **на каком потоке (пуле потоков) выполняется корутина**.

### Основные диспетчеры
1. **`Dispatchers.Main`** — главный (UI) поток. Только для быстрых операций: обновление UI, вызовы `suspend`-функций. Все scoped'ы UI (`lifecycleScope`, `viewModelScope`) живут на Main.
2. **`Dispatchers.IO`** — пул потоков (~64) для блокирующих операций: сеть, БД, файлы, `runBlocking` внутри библиотек.
3. **`Dispatchers.Default`** — пул потоков = числу ядер CPU. Для CPU-intensive работы: парсинг больших JSON, сортировка, обработка изображений, `withContext(Default)` для вычислений.
4. **`Dispatchers.Unconfined`** — стартует на текущем потоке, продолжается на любом, где завершилась предыдущая suspend-функция. Непредсказуем — **не использовать в продакшене**.

### withContext — смена диспетчера
Приостанавливает корутину и переносит её выполнение на другой диспетчер.
```kotlin
suspend fun fetchData(): Data = withContext(Dispatchers.IO) {
    api.getData() // сетевой вызов на IO-пуле
} // возвращаемся на Main, результат присваивается
```
`withContext` не создаёт новую корутину — это та же корутина, сменившая поток.

### Правило для Retrofit / Room
Современные библиотеки с suspend-функциями (Retrofit, Room) сами переключаются на свой диспетчер — оборачивать их в `withContext(Dispatchers.IO)` **не нужно**, это лишнее переключение контекста.

### Типовой вопрос: что будет, если выполнить тяжёлую операцию на Main?
Jank (пропущенные кадры) → ANR (если блокировка > 5 сек). Решение: `withContext(Dispatchers.Default)` для CPU-работы, IO-диспетчер для блокирующих вызовов.

### Производительность
Корутины на `Main` и `Default`/`IO` переключаются дёшево (~сотни наносекунд) через `DispatchedContinuation`. Но лишние `withContext` в горячем коде всё же заметны — диспетчеры не бесплатны на масштабе.
