### Процессы в Android
Каждое приложение работает в **отдельном Linux-процессе** (fork от zygote) с уникальным UID (sandbox). Компоненты одного приложения живут в одном процессе по умолчанию (`android:process=":remote"` позволяет вынести компонент в отдельный процесс — для изоляции памяти/приоритета, но усложняет общение).

### Приоритеты процессов (для решения LMK, кого убить первым)
1. **Foreground** — видимый Activity, foreground service, компонент, к которому привязан foreground-компонент.
2. **Visible** — Activity видна частично (диалог поверх), или foreground service без видимого UI... точнее: видимый, но не интерактивный компонент.
3. **Service** — есть работающий started/bound service.
4. **Cached** — нет активных компонентов; система держит для быстрого перезапуска, первый кандидат на убийство.

Чем ниже приоритет — тем вероятнее процесс будет убит при нехватке памяти.

### LMK (Low Memory Killer)
Два механизма:
- **lmkd (userspace daemon)** — следит за PSI (Pressure Stall Information) / уровнями памяти ядра и убивает процессы согласно oom_adj_score.
- **OOM killer (ядро)** — последний рубеж при исчерпании памяти.

У каждого процесса есть `oom_adj_score`: чем выше (ближе к 1000) — тем «менее нужен» системе. Foreground ~0, cached ~1000. LMKD убивает с наименьшим приоритетом первым.

### Жизненный цикл процесса и приложения
- `Application.onCreate()` вызывается при старте процесса — должен быть быстрым (там инициализируем только критичное; тяжёлую инициализацию — лениво).
- Процесс может быть убит **без вызова onDestroy** — никаких гарантий. Единственное, что переживает смерть процесса: `onSaveInstanceState`/`SavedStateHandle` ( Bundle, ограниченный по размеру ~1 МБ на транзакцию) и persistent storage (БД, файлы, DataStore).

### Вопросы на собесе
- «Почему нельзя хранить большие данные в onSaveInstanceState?» — Binder transaction limit (~1 МБ, общий для процесса), TransactionTooLargeException.
- «Что будет с корутинами при смерти процесса?» — всё умирает, состояние экрана восстанавливается через SavedStateHandle; для восстановления длительных операций — WorkManager (переживает убийство, перезапускает задачу).
- «Как определить, что приложение в фоне?» — ProcessLifecycleOwner, ActivityLifecycleCallbacks (считаем started/stopped Activity), `ActivityManager.getRunningAppProcesses` (устарел/ненадёжен).
