### Что такое рекомпозиция
Compose рисует UI, вызывая composable-функции. Когда меняются использованные внутри состояния — Compose **перезапускает** затронутые функции (recomposition). Аналог invalidate + measure/layout/draw, но на уровне функций.

### Стадии
1. **Composition** — построение дерева UI (вызовы composable).
2. **Layout** — measure + place (как в [[View rendering]]).
3. **Drawing** — отрисовка.

Рекомпозиция может затронуть только composition, layout и drawing могут быть пропущены, если размеры/позиции не изменились.

### Гранулярность
Рекомпозиция идёт **минимально возможной области**: изменилось состояние внутри `Column` — перезапускается только читающие его composable, а не весь экран. Чтение состояния максимально «близко» к месту использования (state hoisting вниз) уменьшает область.

### Скейтинг (skipping)
Compose сравнивает аргументы функции: если все **stable** и равны прежним — пропускает вызов (skippable). Это и есть главная оптимизация.

### Что провоцирует лишние рекомпозиции
1. Нестабильные типы аргументов (см. [[Stability]]).
2. Лямбды-аргументы без remember: каждый вызов — новая лямбда → для неstable-параметров скейтинг ломается.
3. Чтение State в «глубоком» месте: читаем наверху — рекомпозиция всего поддерева; читаем в листе — только лист.
4. `Modifier.offset { }` vs `Modifier.offset(x, y)`: первый — слушание без рекомпозиции каждого кадра (draw-phase based), второй пересоздаёт layout-параметры.

```kotlin
// Хорошо: состояние читается в листе
Column {
    val isVisible by viewModel.isVisible.collectAsStateWithLifecycle()
    Text("Header") // не перекомпонуется при изменении isVisible
    if (isVisible) Text("Body")
}
```

### recomposeScope и restart groups
Каждый composable — restart group; Compose рантайм хранит группы и слот-таблицу (slot table). Обновление state помечает группы, читавшие его, грязными; на следующем кадре они перезапущены.

### Side effects в рекомпозиции
Composable функция должна быть **чистой относительно внешнего мира**: одинаковые входы → одинаковый UI. Побочные эффекты — через `LaunchedEffect`, `SideEffect`, `DisposableEffect`, `rememberUpdatedState` (см. [[Side effects]]).

### Дорогие операции в composition
Composition-код должен быть лёгким: парсинг, аллокации больших объектов, сортировки — наружу (ViewModel/remember + dispatcher). «Работа в композиции» = jank, так как это главный поток.

### Частые вопросы
- «Почему мой список перерисовывается целиком?» — item-функция принимает нестабильный тип / создаётся новый лямбда-аргумент / ключи LazyList нестабильные.
- «Сколько раз вызовется composable?» — сколько угодно, никаких гарантий (как у diffable data source). Поэтому нельзя рассчитывать на порядок/количество вызовов и класть туда логику с эффектами.
