**Model-View-ViewModel** — де-факто стандарт Android-приложений с AAC (Android Architecture Components).

### Роли
- **View** (Activity/Fragment/Compose-функция): отображает состояние, передаёт события пользователя во ViewModel. Максимально «глупая».
- **ViewModel**: хранит состояние экрана (StateFlow), обрабатывает события, обращается к репозиторию. Переживает конфигурационные изменения.
- **Model** (репозиторий/юзкейсы): источник данных (сеть + БД + кэш), ничего не знает про UI.

### Поток данных
```
View --(событие: onRefreshClicked)--> ViewModel --(state: StateFlow)--> View
        ViewModel --> Repository --> (сеть/БД)
```
View подписывается на StateFlow (`collectAsStateWithLifecycle` в Compose, `repeatOnLifecycle` во View). События от пользователя — вызовы публичных методов VM.

### Зачем ViewModel переживает поворот
Данные не перезагружаются при rotation; state сохраняется в StateFlow. При смерти процесса — `SavedStateHandle` для критичного (например, id открытой статьи).

### Типичные ошибки, о которых спрашивают
1. **ViewModel держит ссылку на View/Context** — утечка при destroy (ViewModel живёт дольше View). Для Application Context — допустимо, для Activity — нет.
2. **Бизнес-логика во View** — «анемичная» VM, толстый Fragment.
3. **ViewModel знает про навигацию напрямую** — лучше событие навигации (SharedFlow), а навигацию выполняет View (Compose NavController в UI-слое).
4. **Нет одного источника истины для состояния** — несколько LiveData, которые надо «синхронизировать». Решение: один StateFlow с data class состояния.

### MVVM и двусторонняя связь
Чистый MVVM в Android односторонний по факту (View наблюдает State, VM вызывается напрямую). События «одноразовые» (toast) пробрасываются отдельным SharedFlow.

### Сильные/слабые стороны (для собеса)
- +: простота, официальная поддержка AAC, тестируемость VM.
- -: при росте экрана VM раздувается; состояние может размываться между несколькими LiveData/Flow; навигация и сайд-эффекты легко «протекают» куда попало. Здесь на помощь приходят MVI и юзкейсы.
