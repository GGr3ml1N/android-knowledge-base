**Модульность** — разбиение приложения на Gradle-модули с явными зависимостями. На Senior-собесах спрашивают, когда она окупается и как выглядит граф зависимостей.

### Зачем
1. **Время сборки** — изменение в одном модуле пересобирает только его и зависимые (плюс кэширование).
2. **Скорость команды** — владение модулями, code ownership, изоляция фичей.
3. **Enforced architecture** — границы в коде можно нарушить, границы модулей — нет (нельзя импортировать незадекларированную зависимость).
4. **Переиспользование и изоляция** — instant apps, динамические фичи-модули (Play Feature Delivery), переиспользование в других приложениях компании.

### Типичная структура
```
app/                    — Application-класс, DI-граф, навигация
core/ (shared kernel)   — core-ui, core-network, core-database, core-common
feature/                — feature-feed, feature-auth, feature-profile...
buildSrc/ или build-logic/ — конвенционные плагины, версии зависимостей (version catalog)
```

### Виды модулей
- **App-модуль** — точка сборки, связывает всё.
- **Library-модулей** — обычные (com.android.library / java-library). API и implementation разделены: если модуль B использует класс из `implementation`-зависимости модуля A, B его не видит.
- **Feature-модули (dynamic delivery)** — com.android.dynamic-feature: скачиваются по требованию, сокращают размер базового APK.

### Граф зависимостей (правило)
Зависимости направлены **внутрь**: feature -> core. Фичи **не зависят друг от друга** (feature-feed не знает про feature-profile). Общение фичей — через контракты в core (интерфейсы навигации, общие модели) или app-модуль как координатор.

### DI в многомодульном проекте
Каждый модуль экспортирует свой Dagger-модуль (`@Module`), app-модуль собирает единый `AppComponent`. Вариант с Hilt: `@InstallIn(SingletonComponent::class)` в каждом модуле, Hilt сам агрегирует.

### Gradle-основы, которые спросят в связке
- `implementation` vs `api`: api — транзитивно виден потребителям (публичный контракт), implementation — внутренности (ускоряет сборку, скрывает детали).
- Version Catalog (`libs.versions.toml`) — единое место версий.
- Convention plugins — убрать копипасту build.gradle между модулями.
- Build variants (debug/release), buildConfigField для endpoint'ов.

### Цена модульности (честно)
- Накладные расходы: больше build.gradle-файлов, кросс-модульная навигация, усложнение DI, дублирование ресурсов-утилит если core раздут.
- Не стоит начинать с 50 модулей: эволюция по мере роста команды (монолит -> несколько core + фичи -> полный граф).

### Стандартные вопросы
- «Как передавать данные между фичами?» — не напрямую; через app-координатор/навигацию с аргументами, общие контракты в core-модулях.
- «Как ускорить сборку?» — модуляризация, configuration cache, parallel build, убрать kapt где возможно (KSP), не использовать buildFeatures, которые не нужны (viewBinding в Compose-проекте).
