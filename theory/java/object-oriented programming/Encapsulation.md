**Инкапсуляция** — сокрытие внутреннего состояния объекта и предоставление доступа к нему только через публичный интерфейс (методы). Цель: контроль над данными (валидация, инварианты) и снижение связанности (клиенты не зависят от деталей реализации).

### В Java
Модификаторы доступа + геттеры/сеттеры:
```java
public class Account {
    private double balance; // состояние скрыто

    public void deposit(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("amount must be positive");
        balance += amount; // инвариант защищён
    }
    public double getBalance() { return balance; }
}
```
Без инкапсуляции любой мог бы написать `account.balance = -1000`, нарушив инвариант.

### Модификаторы доступа
| Модификатор | Класс | Пакет | Наследник | Все |
| :--- | :--- | :--- | :--- | :--- |
| `private` | ✓ | | | |
| `default` (package-private) | ✓ | ✓ | | |
| `protected` | ✓ | ✓ | ✓ | |
| `public` | ✓ | ✓ | ✓ | ✓ |

`protected` в Java: доступ наследникам + пакету (в Kotlin `protected` — только наследникам).

### Инкапсуляция ≠ «только private + getters/setters»
Инкапсуляция шире: это скрытие **любых** деталей реализации за абстракцией. Плохой сигнал — «анемичные» сеттеры без логики: `setBalance()` ничем не лучше public-поля. Хороший дизайн: методы предметной области (`deposit`, `withdraw`), состояние меняется только ими.

### Пример нарушения инкапсуляции
Возврат/приём ссылок на изменяемые внутренние объекты:
```java
public List<Item> getItems() { return items; } // клиент может изменить наш список!
```
Решение: `Collections.unmodifiableList(items)` или `new ArrayList<>(items)` (defensive copy). В Kotlin аналогично: приватный `MutableList` + публичный `List`.

### Связь с другими принципами
- Инкапсуляция — основа [[Inheritance|полиморфизма через интерфейсы]]: клиент работает с абстракцией (интерфейс), не зная реализации.
- В Dagger инкапсуляция реализуется через `@Binds`: зависимость объявлена интерфейсом, реализация скрыта в модуле (см. [[Intro]]).
