Классический вопрос собеседований: чем интерфейс отличается от абстрактного класса и что выбрать.

### Сравнение
| | Interface | Abstract class |
| :--- | :--- | :--- |
| Множественное наследование | Да (класс реализует много интерфейсов) | Нет (один суперкласс) |
| Состояние (поля-экземпляры) | Нет (только `public static final` константы) | Да — обычные поля |
| Конструкторы | Нет | Есть |
| Методы | abstract + `default` + `static` (Java 8+) | abstract + concrete |
| Модификаторы членов | public (private методы с Java 9) | Любые |
| «is-a» vs «can-do» | Контракт способностей (`Comparable`, `Serializable`) | Часть иерархии сущностей |

### Примеры из JDK/Android
- Интерфейсы: `Comparable`, `List` (контракт), `OnClickListener`, `Payment` из примера с полиморфизмом.
- Абстрактные: `AbstractList`, `RecyclerView.Adapter` (частичная реализация + состояние), `RoomDatabase`.

### Что выбрать (правила из Effective Java)
1. **Интерфейс** — если нужен контракт без состояния: разные реализации могут быть вообще не связаны иерархией.
2. **Абстрактный класс** — если реализации реально связаны (is-a), нужно разделить код между ними или хранить состояние.
3. Паттерн: интерфейс (контракт) + абстрактный класс-скелет (Skeleton implementation, `AbstractList` + `List`) — гибкость + переиспользование.

### Новое в Java 8+ (часто спрашивают)
- `default` методы: реализация по умолчанию в интерфейсе (`List.sort`). Не ломают обратную совместимость.
- **Diamond problem**: класс реализует два интерфейса с одинаковым default-методом → конфликт, обязан переопределить и выбрать: `Interface1.super.method()`.
- `static` методы в интерфейсах (фабрики, утилиты интерфейса).

### Функциональные интерфейсы (для связи с Kotlin)
Интерфейс с одним abstract-методом — `interface Foo { void bar(); }` → SAM-конверсия: `Foo f = () -> ...`. В Kotlin: `fun interface`. Аннотация `@FunctionalInterface` — проверка компилятором. Это мост к лямбдам Kotlin и к callback-стилю в Android до корутин.

### Kotlin: интерфейсы vs abstract class
- Интерфейсы могут иметь `val`-свойства (абстрактные, без backing field) и default-реализации методов.
- Абстрактный класс — когда нужен state (backing field) + конструктор.
- Композиция через `by` (delegation): `class DbRepo(db: Db) : Repo by db` — композиция с интерфейсным типом, без ручного делегирования.
