## Ответственность слоёв

| Слой | Аннотация | Ответственность |
|---|---|---|
| Controller | `@RestController` | HTTP: маппинг URL, приём параметров, формирование ответа и статуса |
| Service | `@Service` | Бизнес-логика: правила, вычисления, оркестрация |
| Repository | `@Repository` | Доступ к хранилищу (пока внутри сервиса, выделится на уроке JPA) |

- Контроллер не содержит логики предметной области.
- Сервис ничего не знает про HTTP: в нём не используются аннотации web-слоя.

## Поведение вместо данных (Tell, don't ask)

- В Kotlin `val x` компилируется в приватное поле + публичный геттер; на уровне JVM вызов геттера и вызов метода — одинаковые операции. Разница не в механике, а в контракте.
- Публичное свойство выражает: «вот моё устройство — бери и делай что хочешь». Метод выражает: «вот что я умею делать».
- Устройство (список, мапа, запрос к PostgreSQL) — то, что меняется чаще всего. Смена хранения при контракте-методах не трогает вызывающий код; при публичной коллекции — трогает всех вызывающих.
- Логика тянется к слою, владеющему данными: поиск `first { it.id == id }` при переходе на БД становится SQL-запросом и физически не может жить в контроллере.
- Идиома: DTO — публичные свойства без методов (перенос данных — их назначение); сервисы — методы без публичных свойств.

## POST и @RequestBody

- `@PostMapping` — привязка метода к HTTP POST.
- `@RequestBody` — Jackson десериализует тело запроса из JSON в объект указанного типа (обратная операция сериализации ответа).
- Клиент не задаёт серверные поля: id (далее — даты создания, версии) назначает сервер. Поэтому DTO создания ≠ DTO чтения: отдельный класс запроса без id.
- Сигнатура: `fun create(@RequestBody request: CreateWorkoutRequest): WorkoutDto`.
- Статус ответа пока 200 OK; 201 Created — урок про статусы и ошибки.

## Наблюдения из экспериментов

- Непойманное исключение из метода контроллера → Spring ловит на верхнем уровне → 500 для любого исключения. Spring не знает семантики: «не найдено» и «база упала» неотличимы. Отсюда правило: 500 = виноват сервер; «записи нет» — виноват клиент, статус должен быть другим (404).
- JSON при 500 собирает BasicErrorController (auto-configuration, spring-boot-starter-web). В ответе нет текста исключения и стектрейса — сервер не показывает внутренности клиенту (та же инкапсуляция, на границе с внешним миром).
- Неверный тип поля в теле POST (@RequestBody) → отдельный статус 4xx, зафиксировать экспериментально.
