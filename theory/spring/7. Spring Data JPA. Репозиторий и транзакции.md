# Урок 7. Spring Data JPA: репозиторий и транзакции

## Зачем Spring Data JPA

- Чистый JPA: работа через EntityManager, одинаковый boilerplate в каждом DAO.
- Spring Data JPA: объявляешь интерфейс — реализация генерируется автоматически (proxy в рантайме). Методы получаются из имени или объявляются вручную.

## Репозиторий

- `interface WorkoutRepository : JpaRepository<WorkoutEntity, Long>` (org.springframework.data.jpa.repository.JpaRepository). Два generic-параметра: тип сущности и тип её id.
- Готовые методы из коробки:

| Метод | Что делает |
|---|---|
| `save(entity)` | INSERT, если сущность новая (id = 0); UPDATE, если загруженная (id != 0) |
| `findById(id)` | Поиск по PK, возвращает `Optional<Entity>` |
| `findAll()` | Все записи |
| `deleteById(id)` | Удаление по PK |
| `count()`, `existsById(id)` | Статистика и проверка |

- Новая vs загруженная сущность: у новой id = 0 (значение по умолчанию) → persist/INSERT; у загруженной из БД id != 0 → merge/UPDATE. Поэтому в create id не присваивают — выдаст база (IDENTITY).
- `Optional<Entity>` (java.util.Optional) — контейнер «значение или отсутствие»:

```kotlin
val entity = repository.findById(id).orElseThrow { WorkoutNotFoundException(id) }
```

- Производные методы: имя метода парсится в запрос, реализация не нужна:

```kotlin
fun findByStartTimestampBetween(start: Long, end: Long): List<WorkoutEntity>
fun findByNameContainingIgnoreCase(name: String): List<WorkoutEntity>
```

## Как парсится имя метода

Грамматика: префикс + By + путь свойства + оператор + модификаторы; соединение через And/Or; сортировка через OrderBy.

| Часть имени | Что генерирует |
|---|---|
| `find...By` / `read...By` / `query...By` | Начало запроса (синонимы) |
| `findByName` | WHERE name = ? |
| `findByStartTimestampBetween` | WHERE start_timestamp BETWEEN ? AND ? |
| `findByNameContainingIgnoreCase` | WHERE lower(name) LIKE lower('%...%') |
| `findByNameContainingOrNameStartingWith` | WHERE ... OR ... |
| `findDistinctByName` | SELECT DISTINCT ... |
| `findByNameOrderByStartTimestampDesc` | ... ORDER BY start_timestamp DESC |
| `findTop5By...` / `findFirstBy...` | LIMIT 5 / LIMIT 1 |

- Путь свойства может спускаться по связям: `findByWorkoutName(...)` у WorkoutExerciseEntity — пройдёт по полю workout, затем name.
- Опечатка в имени свойства → падение при старте контекста (fail-fast): схему сущностей проверяют на этапе поднятия, а не при первом запросе.
- Механика: прокси репозитория на старте строит JPA Criteria-запрос из имени, затем → SQL. Никакой магии в рантайме — всё разрешено заранее.

## @Query: явные запросы

- JPQL — язык запросов по классам и полям сущностей (не таблицам и колонкам). `w` в примерах ниже — алиас (псевдоним) сущности, придуманный автором запроса: после `FROM WorkoutEntity w` поля доступны как `w.имяПоля` (роль та же, что у `it` в лямбде, или у алиаса таблицы в SQL). `SELECT w` — выбрать сущность целиком.

```kotlin
@Query("SELECT w FROM WorkoutEntity w WHERE w.startTimestamp BETWEEN :start AND :end")
fun findBetween(
    @Param("start") start: Long,
    @Param("end") end: Long
): List<WorkoutEntity>

@Query("SELECT w FROM WorkoutEntity w WHERE w.name LIKE %:part% ORDER BY w.startTimestamp DESC")
fun search(@Param("part") part: String): List<WorkoutEntity>
```

- Именованные параметры `:name` связываются через `@Param` (org.springframework.data.repository.query.Param).
- `nativeQuery = true` — сырой SQL по таблицам и колонкам. Проверяется только при выполнении (не при старте), поэтому опечатку в колонке увидишь в рантайме:

```kotlin
@Query(
    value = "SELECT * FROM workout WHERE start_timestamp BETWEEN :start AND :end",
    nativeQuery = true
)
fun findBetweenNative(
    @Param("start") start: Long,
    @Param("end") end: Long
): List<WorkoutEntity>
```

- Выбор инструмента: производные методы — простые условия; @Query — joins, агрегации, нестандартный SQL; Criteria API — динамический запрос с переменным числом условий (позже).
- Эвристика: условие читается как имя метода — пишем derived; имя превращается в простыню (цепочки And/Or, OrderBy) — @Query читабельнее. Смешивать оба подхода в одном репозитории — норма.

## Пример: репозиторий целиком (домен Note)

Производные методы и @Query мирно соседствуют в одном интерфейсе. Обрати внимание на анти-пример в конце — именно так выглядит derived-метод, который пора переписать в @Query.

```kotlin
interface NoteRepository : JpaRepository<NoteEntity, Long> {

    // простые условия — производные методы
    fun findByTitleContainingIgnoreCase(fragment: String): List<NoteEntity>
    fun findByCreatedAtBetween(start: Long, end: Long): List<NoteEntity>
    fun findTop3ByOrderByCreatedAtDesc(): List<NoteEntity>

    // условие, которое именем метода выражать неудобно — @Query
    @Query("SELECT n FROM NoteEntity n WHERE length(n.content) > :minLength")
    fun findLongNotes(@Param("minLength") minLength: Int): List<NoteEntity>

    // АНТИ-ПРИМЕР: имя превратилось в простыню — такое читается @Query легче:
    // fun findByTitleContainingIgnoreCaseOrContentContainingIgnoreCaseOrderByCreatedAtDesc(...)
}
```

## Транзакции

- `@Transactional` (org.springframework.transaction.annotation.Transactional) на методе сервиса: всё выполняется в одной транзакции БД. Коммит — при нормальном выходе; откат — при вылете RuntimeException.
- `readOnly = true` — для методов чтения: подсказка драйверу и пулу соединений.
- Граница транзакции = граница бизнес-операции, поэтому аннотация на сервисе:
  - на репозитории каждый метод был бы отдельной транзакцией — бизнес-операция из нескольких записей перестала бы быть атомарной (часть записалась, часть нет);
  - на контроллере транзакция затянула бы HTTP-слой, а один endpoint может требовать нескольких независимых операций;
  - сервисный метод может сделать несколько запросов к разным таблицам — они должны пройти либо все, либо ни одного.

Пример атомарности (два UPDATE — одно целое; если второй упадёт, первый откатится):

```kotlin
@Transactional
fun transfer(fromId: Long, toId: Long, amount: Long) {
    accountRepository.debit(fromId, amount)   // UPDATE
    accountRepository.credit(toId, amount)    // UPDATE — упадёт здесь → debit откатится
}
```

## Маппинг Entity ↔ DTO

- Сущности не покидают сервис: контроллер работает только с DTO. Причины: схема БД и контракт API эволюционируют независимо; сущность несёт аннотации персистентности и ленивые прокси — сериализация её в JSON ломается или тянет за собой пол-БД.
- Пока маппинг ручной — функции-конвертеры (extension-функции удобны). Библиотеки вроде MapStruct — позже.

```kotlin
fun WorkoutEntity.toDto() = WorkoutDto(id = id, name = name, date = startTimestamp)
fun CreateWorkoutRequest.toEntity() = WorkoutEntity(name = name, startTimestamp = date)
```

## Пример: сервис целиком (домен Note)

Сквозной стиль слоя данных: репозиторий в конструкторе, @Transactional на каждом методе, маппинг на границах, Optional → orElseThrow.

```kotlin
@Service
class NoteService(private val noteRepository: NoteRepository) {

    @Transactional(readOnly = true)
    fun getAll(): List<NoteDto> =
        noteRepository.findAll().map { it.toDto() }

    @Transactional(readOnly = true)
    fun getById(id: Long): NoteDto {
        val entity = noteRepository.findById(id)
            .orElseThrow { NoteNotFoundException(id) }
        return entity.toDto()
    }

    @Transactional
    fun create(request: CreateNoteRequest): NoteDto =
        noteRepository.save(request.toEntity()).toDto()
}

fun NoteEntity.toDto() = NoteDto(id = id, title = title, createdAt = createdAt)
fun CreateNoteRequest.toEntity() = NoteEntity(title = title, content = content)
```

## Состав слоёв после перехода на БД

```
Controller (DTO)  →  Service (DTO ↔ Entity, @Transactional, правила)  →  Repository (Entity)  →  PostgreSQL
```
