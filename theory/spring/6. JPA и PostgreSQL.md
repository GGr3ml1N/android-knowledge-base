## Зачем ORM и связи

- Реляционная модель: строки в таблицах, связи через внешние ключи, данные собираются JOIN-ами. Объектная модель: граф объектов, связи — ссылки на другие объекты. Это несоответствие называют object-relational impedance mismatch — JPA (Jakarta Persistence) существует, чтобы закрыть его.
- ORM превращает строки таблиц в объекты и обратно (Hibernate — реализация). Связи (`@ManyToOne` и др.) заменяют ручную работу с FK: вместо «колонка workout_id + JOIN в каждом запросе» — обычное поле-объект.
- Каскады переносят `ON DELETE CASCADE` с уровня SQL на уровень объектов: операция над родителем распространяется на детей.

## Стек технологий

| Компонент | Что это | Роль |
|---|---|---|
| JPA (Jakarta Persistence) | Спецификация ORM | Стандарт: объекты ↔ таблицы, аннотации |
| Hibernate | Реализация JPA | Идёт в составе spring-boot-starter-data-jpa, выполняет SQL |
| Spring Data JPA | Надстройка над Hibernate | Репозитории-интерфейсы вместо ручного DAO (следующий шаг) |

## Entity

- `@Entity` (jakarta: `jakarta.persistence.Entity`) — класс, привязанный к таблице. Имя таблицы по умолчанию = имени класса.
- `@Table(name = "...", schema = "...")` — переопределение имени таблицы.
- `@Id` — первичный ключ.
- `@GeneratedValue` — генерация id. Стратегии:

| Стратегия | Как работает | Когда |
|---|---|---|
| `IDENTITY` | id из autoincrement-колонки БД (INSERT без id, БД возвращает) | Таблицы с AUTOINCREMENT/IDENTITY/SERIAL |
| `SEQUENCE` | id из sequence БД (отдельный объект, выдаёт пачки) | PostgreSQL-ориум, default для Hibernate 6 при `AUTO` |
| `TABLE` | Эмуляция sequence отдельной таблицей | Устаревшая, не использовать |
| `AUTO` | Выбор провайдером (в Hibernate 6 ≈ SEQUENCE) | Когда схема БД не фиксирована |

- `@Column(name, nullable, unique, length, insertable, updatable)` — тонкая настройка колонки; имя camelCase → snake_case подставляется автоматически (`startTimestamp` → `start_timestamp`).

```kotlin
@Entity
@Table(name = "product")
class ProductEntity(
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    var id: Long = 0,
    @Column(nullable = false, length = 200)
    var title: String = "",
    var priceCents: Int = 0
)
```

- Требования JPA к классу: не-final класс + no-arg конструктор (Hibernate создаёт прокси и подменяет значения).
- Kotlin: плагин `kotlin("plugin.jpa")` (no-arg + all-open для сущностей); свойства — `var` со значениями по умолчанию. В отличие от DTO (`val`), сущности — не иммутабельные данные, а объекты, которыми управляет провайдер.
- Принятый паттерн конструктора: поля, которые задаёт приложение (name, startTimestamp), — параметры primary constructor с дефолтами; id (выдаёт база) и коллекции связей — свойства в теле класса. No-arg конструктор для JPA сохраняется: Kotlin генерирует его, т.к. все параметры имеют дефолты (плюс no-arg-плагин).
- Встречающийся в туториалах стиль «все параметры в конструкторе без дефолтов, non-null» работает только при включённом kotlin("plugin.jpa"): его синтетический конструктор вызывает основной с null/0, после чего Hibernate заполняет поля рефлексией. Подвохи: окно между созданием и заполнением, где non-null поля физически null (NPE при чтении из init-блока/метода конструктора); сигнатура врёт о non-null; без плагина — InstantiationException при первой загрузке. Стиль с дефолтами честнее отражает жизненный цикл сущности.
- Рефлексия вокруг null-safety: Hibernate создаёт и заполняет сущности в обход конструктора и геттеров Kotlin, поэтому иммутабельность (val) для сущностей недоступна — только var.

## Типы связей

Термины: **владеющая сторона** (owning side) — та, где физически лежит внешний ключ. **Обратная сторона** — зеркальное поле, указывает на владеющую через `mappedBy`.

| Связь | Смысл | Владеющая сторона | Join-таблица |
|---|---|---|---|
| `@ManyToOne` | много объектов к одному (N→1) | сама аннотация (FK здесь) | нет |
| `@OneToMany` | один ко многим (1→N) | обратная, через `mappedBy` | нет |
| `@OneToOne` | один к одному (1↔1) | где стоит FK | нет |
| `@ManyToMany` | многие ко многим (N↔N) | любая, через `@JoinTable` | создаётся автоматически |

### @ManyToOne

Самая частая связь. Много товаров в одной категории — FK `category_id` в таблице товара:

```kotlin
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "category_id")
var category: CategoryEntity? = null
```

- `fetch` — когда подгружать (см. раз про fetch).
- `optional = false` — связь обязательная → колонка NOT NULL.
- `@JoinColumn(name, nullable, unique, referencedColumnName)` — настройка колонки FK.

### @OneToMany

Обратная сторона связи. Без `mappedBy` Hibernate создаст лишнюю join-таблицу — классическая ошибка:

```kotlin
@OneToMany(mappedBy = "category", cascade = [CascadeType.ALL], orphanRemoval = true)
var products: MutableList<ProductEntity> = mutableListOf()
```

- `mappedBy = "category"` — имя поля владеющей стороны (поле `category` в ProductEntity).
- `cascade` — распространять операции на детей (см. раз про каскады).
- `orphanRemoval = true` — удаление ребёнка из коллекции = DELETE из БД.

### @OneToOne

Профиль пользователя: расширение сущности без раздувания одной таблицы. Владеющая сторона — где FK (обычно у «детали»):

```kotlin
@OneToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "profile_id")
var profile: ProfileEntity? = null
```

### @ManyToMany

Товары и теги: ни у кого нет колонки для FK, поэтому JPA создаёт join-таблицу:

```kotlin
// владеющая сторона
@ManyToMany
@JoinTable(
    name = "product_tag",
    joinColumns = [JoinColumn(name = "product_id")],
    inverseJoinColumns = [JoinColumn(name = "tag_id")]
)
var tags: MutableSet<TagEntity> = mutableSetOf()

// обратная сторона
@ManyToMany(mappedBy = "tags")
var products: MutableSet<ProductEntity> = mutableSetOf()
```

- Замечание: join-таблицы не умеют хранить дополнительные поля (дата добавления, порядок). Как только появляется payload — ManyToMany превращают в две связи ManyToOne через промежуточную сущность.

## Как читать названия связей

- Название аннотации читается от первого лица класса, в котором стоит: первая часть — сколько «нас», вторая — сколько «их».
- Пример: отдел и сотрудники. Связь в БД хранится один раз — колонка `department_id` в таблице `employee`.

```kotlin
@Entity
class EmployeeEntity(
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    var id: Long = 0,
    var name: String = "",

    // Employee смотрит на свою колонку FK:
    // «много таких как я ссылаются на один отдел» → ManyToOne
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")
    var department: DepartmentEntity? = null
)

@Entity
class DepartmentEntity(
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    var id: Long = 0,
    var name: String = "",

    // Department смотрит на ту же колонку с обратной стороны:
    // «один отдел — много сотрудников» → OneToMany
    @OneToMany(mappedBy = "department")
    var employees: MutableList<EmployeeEntity> = mutableListOf()
)
```

- Одна и та же связь (одна колонка FK) описывается дважды — по разу с каждой стороны навигации: `employee.department` и `department.employees`.
- Владеющая сторона (где физически лежит FK) — всегда `@ManyToOne`; обратная — `@OneToMany` с `mappedBy` = имя поля другого класса (не колонки).
- `@OneToMany` — зеркало без собственной колонки: Hibernate собирает коллекцию запросом `WHERE department_id = ?`.
- Если `mappedBy` забыть, Hibernate создаст лишнюю join-таблицу.
- Мнемоника: FK живёт там, где `@ManyToOne`.

## Откуда JPA знает тип целевой сущности

- Тип элемента коллекции выводится из generic-параметра: `MutableList<EmployeeEntity>` → цель `EmployeeEntity`. Параметр `targetEntity` в `@OneToMany` указывать не нужно — он дублирует тип и нужен только для raw-типов (`List` без `<...>`, эпоха до дженериков).
- У `@ManyToOne` тип берётся прямо из объявления поля (`var department: DepartmentEntity`).
- Полная цепочка разрешения `@OneToMany(mappedBy = "department")`: generic-параметр → целевой класс → поле `department` в нём → его `@JoinColumn` → колонка FK, по которой собирается коллекция.

## Каскады

| CascadeType | Что распространяется на детей |
|---|---|
| `PERSIST` | Сохранение (INSERT) |
| `MERGE` | Обновление (UPDATE) |
| `REMOVE` | Удаление (DELETE) |
| `REFRESH` | Перечитывание из БД |
| `DETACH` | Отключение от контекста персистентности |
| `ALL` | Всё перечисленное |

- `orphanRemoval = true` vs `REMOVE`: REMOVE удаляет детей, только когда удаляют родителя; orphanRemoval удаляет ребёнка, как только он исчез из коллекции родителя. Для жёсткой композиции («дети не существуют без родителя») — оба.

## Fetch: LAZY vs EAGER

| Аннотация | Значение по умолчанию | Рекомендация |
|---|---|---|
| `@ManyToOne`, `@OneToOne` | `EAGER` | Писать `LAZY` явно |
| `@OneToMany`, `@ManyToMany` | `LAZY` | Оставлять |

- `EAGER` — связанный объект грузится тем же запросом (JOIN), всегда, нужен ли он или нет.
- `LAZY` — прокси, реальная загрузка только при первом обращении к полю.
- Ловушка N+1: LAZY-коллекция у 100 объектов → при обходе 100 дополнительных запросов. Решения: `JOIN FETCH` в запросе, `@EntityGraph` — отдельная тема.

## Полный пример двусторонней связи

```kotlin
@Entity
@Table(name = "category")
class CategoryEntity(
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    var id: Long = 0,
    var name: String = "",

    @OneToMany(mappedBy = "category", cascade = [CascadeType.ALL], orphanRemoval = true)
    var products: MutableList<ProductEntity> = mutableListOf()
)

@Entity
@Table(name = "product")
class ProductEntity(
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    var id: Long = 0,
    var title: String = "",

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "category_id")
    var category: CategoryEntity? = null
)
```

## Подключение PostgreSQL

- Контейнер: `docker run --name fitness-postgres -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=fitness -p 5432:5432 -d postgres:17` (или существующий контейнер + отдельная база `CREATE DATABASE fitness;` — старые данные не трогать).
- application.yaml:

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/fitness
    username: postgres
    password: postgres
  jpa:
    hibernate:
      ddl-auto: update   # учебно; в проде — миграции Flyway
    show-sql: true       # печатать SQL в лог
```

## Порядок проверки

1. Приложение стартует без ошибок конфигурации `DataSource`.
2. В логах — DDL-операции Hibernate (CREATE TABLE).
3. Список таблиц в БД содержит таблицы сущностей (через Beekeeper Studio или `docker exec -it <контейнер> psql -U <юзер> -d fitness -c '\dt'`).
