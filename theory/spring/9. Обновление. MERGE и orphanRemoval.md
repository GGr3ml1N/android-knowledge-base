## Семантика PUT

- PUT = полная замена ресурса по id: клиент присылает дерево целиком, сервер приводит хранимое состояние к присланному. Идемпотентен: повтор того же запроса — то же состояние.
- Тело — как в POST, но у существующих детей есть id, у новых — нет. Отсюда требование к request-DTO: id детей nullable (`Long?`): null = создать, не null = обновить.
- Ответ: 200 + обновлённое дерево (переиспользуем чтение из урока 8) или 204 без тела. Берём 200 с деревом.

## Ключевая идея: работаем с managed-сущностью

- Внутри `@Transactional` загруженная сущность находится под управлением сессии (managed). Hibernate ведёт её снимок и на флаше сравнивает с текущим состоянием — **dirty checking**: сам выдаст UPDATE для изменённых полей, INSERT для новых детей, DELETE для удалённых из коллекций (при orphanRemoval).
- Значит, в update-методе **нет ни одного вызова save** — достаточно изменить managed-объект. `save` нужен только для новых (transient) корней.

## Алгоритм синхронизации дерева

1. Найти тренировку по id — нет → 404 (WorkoutNotFoundException).
2. Обновить скалярные поля: name, startTimestamp.
3. Синхронизировать упражнения:
   - пришёл с id → найти в текущей коллекции по id, обновить его поля;
   - пришёл без id → создать сущность, проставить обе стороны связи, добавить в коллекцию;
   - не пришёл вообще → кандидат на удаление.
4. Удаление: снять «не пришедшие» элементы в отдельный список, потом убрать их из коллекции. Убранный элемент при orphanRemoval → DELETE на флаше.
5. То же самое рекурсивно для подходов каждого упражнения.
6. Коммит по выходу из метода (flush автоматический). Вернуть свежее дерево через тот же `getWorkoutById`.

Скелет сервиса:

```kotlin
@Transactional
fun updateWorkout(id: Long, request: WorkoutRequest): WorkoutDto {
    val workout = workoutRepository.findByIdWithExercises(id)
        ?: throw WorkoutNotFoundException(id)

    workout.name = request.name
    workout.startTimestamp = request.startTimestamp

    syncExercises(workout, request.workoutExercises)
    // syncRepBlocks — внутри syncExercises для каждого упражнения

    return getWorkoutById(id)   // перечитываем управляемый граф и мапим
}
```

## Почему не «собрать новое дерево и save()»

Ложный путь: сконструировать `WorkoutEntity` из DTO (со всеми детьми) и `save()`. Такой объект — detached: сессия о нём ничего не знает, save делает merge. Для коллекций detached-объекта Hibernate не может отличить «тот же ребёнок с правками» от «удалить старый, вставить новый» — и на флаше получается лавина DELETE+INSERT всего поддерева, теряются FK-контракты, возможны конфликты PK. Ручная синхронизация managed-сущности предсказуема: каждое изменение явно.

## orphanRemoval на практике

- Убираем ребёнка из managed-коллекции → Hibernate помечает его orphan → DELETE при флаше. Работает, потому что каскад идёт от коллекции родителя.
- Обратная сторона: дети существуют, пока в коллекции. Удаление напрямую через репозиторий, минуя родителя, — отдельная история (нарушение инварианта коллекции).

## Ловушки

| Ошибка | Симптом |
|---|---|
| Удалять из коллекции, итерируясь по ней | ConcurrentModificationException |
| Собрать дерево из DTO и save() | Лавина DELETE+INSERT на флаше |
| Забыть orphanRemoval | «Осиротевшие» строки остаются в БД |
| Менять поля несуществующего id без проверки | Случайный INSERT вместо 404 |

## Почему бросает ConcurrentModificationException

- `for` по коллекции в Kotlin/JVM компилируется в цикл с итератором. Итераторы стандартных коллекций (`java.util.ArrayList` и др.) **fail-fast**: при создании запоминают `modCount` — счётчик структурных изменений.
- `add`/`remove` через саму коллекцию увеличивают `modCount`. При следующем вызове `next()` итератор сравнивает ожидаемый и текущий `modCount` — расходятся → `ConcurrentModificationException`.
- Это **однопоточный** механизм защиты от порчи обхода. К многопоточности и к базе данных отношения не имеет: то же самое произойдёт с обычным `ArrayList` в чистой JVM.
- У managed-коллекций Hibernate (`PersistentBag` и др.) поведение то же — под капотом обычный список.
- Как удалять безопасно:
  - отдельный список на удаление + `removeAll` после цикла (подход урока);
  - `iterator.remove()` — итератор сам корректно снимает элемент;
  - `removeIf { ... }` — внутри тоже идёт через `iterator.remove()`;
  - индексный цикл в обратном порядке (`for (i in list.indices.reversed())`) — индексы сдвигаются только у уже пройденных элементов.
- Ловушка индексного цикла с удалением в прямом порядке: после `removeAt(i)` элементы сдвигаются, следующий элемент занимает текущий индекс и пропускается — баг без исключения, находится только глазами.

- PUT vs PATCH: PATCH — частичное обновление (только присланные поля). В курсе не нужен, но знать термин стоит.

## Проверка глазами

- `show-sql`: на корректный PUT — только нужные операции (UPDATE родителя, пара UPDATE детей, DELETE убранных, INSERT новых). Лавина DELETE+INSERT = что-то пошло по ложному пути.
- Beekeeper: удалённое исчезло, новое появилось с заполненными FK.
