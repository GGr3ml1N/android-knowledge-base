# Урок 8. Вложенная модель: каскады, обратные ссылки, N+1

## Цель

Одним запросом создать тренировку вместе с упражнениями и подходами; одним запросом получить всё дерево. В терминах схемы: запись в три таблицы за один POST.

## Каскады: все типы и когда какой ставить

Каскад = «операция над родителем автоматически применяется к детям из коллекции». Типы:

| CascadeType | Что распространяется на детей | Типичный случай |
|---|---|---|
| `PERSIST` | INSERT (save нового родителя сохраняет и детей) | Создание дерева одним save |
| `MERGE` | UPDATE (merge родителя обновляет и детей) | Обновление дерева из DTO (PUT целиком) |
| `REMOVE` | DELETE при удалении родителя | Жёсткая композиция: дети бессмысленны без родителя |
| `REFRESH` | Перечитывание из БД, откат незакоммиченных изменений | Редко: ручное управление при конкурентном доступе |
| `DETACH` | Отключение от сессии вместе с родителем | Редко: ручное управление сессией |
| `ALL` | Всё перечисленное | Композиция по умолчанию |

- REFRESH и DETACH — специальные, в обычном CRUD не нужны.
- `orphanRemoval = true` vs `REMOVE`: REMOVE срабатывает при удалении РОДИТЕЛЯ; orphanRemoval — при удалении ребёнка ИЗ КОЛЛЕКЦИИ (delete родительский список.remove(child) → DELETE строки ребёнка).

### Главное правило: композиция vs ссылка

| Отношение | Пример | Каскад |
|---|---|---|
| Композиция: дети не существуют без родителя, живут и умирают вместе с ним | Заказ → позиции; Тренировка → упражнения → подходы | `ALL` + `orphanRemoval = true` |
| Ссылка на самостоятельную сущность, которую используют многие | Заказ → товар (Product); Комментарий → автор (User) | Без каскада |

Если поставить ALL на ссылку — удаление заказа удалит товар из каталога. Каскад отвечает на вопрос: «если я удалю/сохраню родителя, должны ли дети следовать за ним?» Для тренировки и её упражнений — да. Для товара в заказе — нет.

## Полный сквозной пример (домен Order/OrderItem)

### Запрос

```json
POST /orders
{
  "customerName": "Иван",
  "items": [
    {"sku": "BOOK-1", "quantity": 2, "priceCents": 1500},
    {"sku": "PEN-7", "quantity": 1, "priceCents": 300}
  ]
}
```

### DTO запроса

```kotlin
data class CreateOrderRequest(
    @field:NotBlank val customerName: String,
    @field:NotEmpty val items: List<@Valid OrderItemRequest>
)

data class OrderItemRequest(
    @field:NotBlank val sku: String,
    @field:Positive val quantity: Int,
    @field:PositiveOrZero val priceCents: Int
)
```

### Сущности

```kotlin
@Entity
@Table(name = "orders")
class OrderEntity(
    var customerName: String = ""
) {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    var id: Long = 0

    @OneToMany(mappedBy = "order", cascade = [CascadeType.ALL], orphanRemoval = true)
    var items: MutableList<OrderItemEntity> = mutableListOf()
}

@Entity
@Table(name = "order_item")
class OrderItemEntity(
    var sku: String = "",
    var quantity: Int = 0,
    var priceCents: Int = 0
) {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    var id: Long = 0

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id")
    var order: OrderEntity? = null
}
```

### Сервис: сборка дерева

```kotlin
@Transactional
fun create(request: CreateOrderRequest): OrderDto {
    val order = OrderEntity(customerName = request.customerName)

    for (itemRequest in request.items) {
        val item = OrderItemEntity(
            sku = itemRequest.sku,
            quantity = itemRequest.quantity,
            priceCents = itemRequest.priceCents
        )
        item.order = order       // обратная ссылка → значение для колонки order_id
        order.items.add(item)    // вторая сторона → каскад увидит ребёнка
    }

    return orderRepository.save(order).toDto()
}
```

### Что выполнится в БД (видно по show-sql)

```
INSERT INTO orders (customer_name) VALUES ('Иван')                       -- id выдан БД
INSERT INTO order_item (order_id, sku, quantity, price_cents) VALUES (1, 'BOOK-1', 2, 1500)
INSERT INTO order_item (order_id, sku, quantity, price_cents) VALUES (1, 'PEN-7', 1, 300)
```

Один save → три INSERT в одной транзакции. Родитель идёт первым: детям нужен его id для FK.

## Почему обязательны ОБЕ стороны связи

| Действие | Зачем | Если пропустить |
|---|---|---|
| `order.items.add(item)` | Каскад идёт от коллекции: save(order) «видит» только тех детей, что в списке | Дети вообще не вставятся — молча, без ошибки |
| `item.order = order` | Значение для колонки `order_id` берётся из поля владеющей стороны | INSERT детей с `order_id = NULL` → связь потеряна (или нарушение NOT NULL) |

## LAZY, прокси и N+1 — подробно

### Что такое ленивая коллекция физически

При загрузке заказа Hibernate выполняет только:

```sql
select o.id, o.customer_name from orders o where o.id = 1
```

Полю `items` присваивается НЕ список, а прокси-объект (PersistentBag) — пустая заглушка, которая знает: «мне положено содержимое, но его ещё никто не просил». Запроса за позициями не было.

### Шаг за шагом: как 1 запрос превращается в каскад запросов

1. `orderRepository.findById(1)` → запрос 1: заказ. Коллекция — прокси.
2. Маппер трогает `order.items` → прокси «просыпается» → запрос 2: `select ... from order_item where order_id = 1`.
3. Для каждой позиции маппер трогает её ленивые связи → запросы 3, 4, ...: по одному на элемент.

Запросы выполняются не в момент findById, а по мере того, как маппер (или любой другой код) обращается к прокси. Поэтому проблема называется «N+1» (1 запрос за родителем + N запросов за детьми) — и её количество зависит от данных.

### Подсчёт для трёхуровневого дерева

Тренировка → 3 упражнения, у каждого 2 подхода, список из 10 тренировок:

| Шаг | Запросов | Что |
|---|---|---|
| findAll() | 1 | 10 тренировок |
| маппинг упражнений | 10 | по одному на тренировку |
| маппинг подходов | 30 | по одному на каждое из 30 упражнений |
| Итого | **41** | вместо 3 |

С ростом данных растёт и число запросов — это делает endpoint медленным непредсказуемо.

## JOIN FETCH: как сжать всё в один запрос

```kotlin
@Query("SELECT o FROM OrderEntity o LEFT JOIN FETCH o.items WHERE o.id = :id")
fun findByIdWithItems(@Param("id") id: Long): OrderEntity?
```

`JOIN FETCH` говорит: «в этом же запросе заодно вытащи коллекцию». SQL становится одним:

```sql
select o.id, o.customer_name, i.id, i.sku, i.quantity, i.price_cents
from orders o
left join order_item i on o.id = i.order_id
where o.id = 1
```

Результат — две строки (позиции продублировали заказ), Hibernate сам «склеивает» их обратно в один объект с коллекцией из двух элементов. Программно для нас ничего не меняется — меняется только число запросов: 2 → 1.

- Для списков с JOIN FETCH нужен `DISTINCT` в JPQL (`SELECT DISTINCT o ...`), иначе один заказ вернётся по разу на каждую позицию.
- Альтернатива объявлениями: `@EntityGraph(attributePaths = ["items"])` на derived-методе — тот же эффект.

## Две вложенные коллекции: почему один JOIN FETCH невозможен

Представь тренировку с 3 упражнениями и 6 подходами. Один join:

```sql
... left join workout_exercise we on ... 
```

даёт 3 строки на тренировку. Добавим второй join — подходы:

```sql
... left join workout_exercise we on ...
    left join rep_block rb on ...
```

Каждая строка упражнения склеивается с КАЖДЫМ его подходом: 3 упражнения × подходы каждого = данные раздуваются многократно, в памяти строки дублируются декартовым произведением. Для двух `List`-коллекций Hibernate встречает `MultipleBagFetchException` и отказывается.

Решение — разбить на два запроса: родитель + первая коллекция одним JOIN FETCH, вторая коллекция — вторым запросом пачкой для всех элементов первой:

```kotlin
@Query("SELECT rb FROM RepBlockEntity rb WHERE rb.workoutExercise IN :exercises")
fun findByWorkoutExerciseIn(
    @Param("exercises") exercises: List<WorkoutExerciseEntity>
): List<RepBlockEntity>
```

Дерево из трёх уровней собирается за 2 запроса вместо 41. Альтернатива — `@org.hibernate.annotations.BatchSize(size = 50)` на коллекции: ленивые коллекции докидываются пачками по N элементов, а не по одному (итог для нашего случая: 1 + 1 + 1).

## LazyInitializationException — подробно

### Хронология ошибки

1. Транзакция сервиса открылась, сессия Hibernate создана.
2. Загружен заказ, коллекция items — прокси.
3. Метод сервиса завершился: транзакция закрылась, сессия уничтожена.
4. В контроллере (вне транзакции) маппер обращается к `order.items` → прокси пытается выполнить запрос, но сессии нет:

```
org.hibernate.LazyInitializationException: failed to lazily initialize a collection of role:
OrderEntity.items, could not initialize proxy - no Session
```

Ленивый прокси может работать, только пока жива сессия. Отсюда правило: весь обход графа сущностей и маппинг в DTO — внутри транзакции сервиса, до её закрытия.

### Нюанс Spring Boot: open-in-view

По умолчанию Spring Boot включает `spring.jpa.open-in-view=true`: сессия держится открытой до конца HTTP-запроса, поэтому обращение к ленивой коллекции в контроллере может «просто работать». Это страховка-антпаттерн: она маскирует нарушение слоёв и провоцирует N+1 на уровне представления. В серьёзных проектах её выключают (`open-in-view: false`), и тогда правило «мапим только внутри транзакции» становится железным. Правильный стиль не зависит от этой настройки — маппинг всегда в сервисе.

## Секреты в конфигурации

- application.yaml попадает в git — значит, секреты в нём видны всем, у кого есть доступ к репозиторию.
- Правило: в yaml — плейсхолдеры, значения — из переменных окружения:

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/fitness
    username: ${DB_USER}
    password: ${DB_PASSWORD}
```

- Локально env-переменные задают в конфигурации запуска IDEA (Run → Edit Configurations → Environment variables) или через .env-файл (не коммитить).
- Для локальной учебной БД риск невысок (localhost), но привычка «секреты не в git» формируется с первого дня.
- В проде: менеджеры секретов (Vault, облачные Secret Manager) — отдельная тема.
