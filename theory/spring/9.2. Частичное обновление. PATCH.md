## Семантика: PATCH vs PUT

| | PUT | PATCH |
|---|---|---|
| Смысл | Полная замена ресурса по id | Частичное обновление: применяются только присланные поля |
| Тело | Целостное состояние ресурса (и дерева целиком) | Только изменяемые поля |
| Неприсланное поле | Считается «сбросить/удалить» (у нас: дети без id — на удаление) | Остаётся как есть |
| Идемпотентность | Гарантирована: повтор того же запроса = то же состояние | Зависит от семантики операции (RFC 5789 не гарантирует) |
| Ответ | 200 + обновлённый ресурс или 204 | То же: 200 + ресурс или 204 |
| Типичная ошибка | «Затёрть» то, что клиент не прислал | Применить null как «не трогать», когда имелось в виду «очистить поле» |

- Для вложенных структур PUT удобен (дерево заменяется целиком), PATCH — для плоских правок отдельных сущностей или скаляров.
- PATCH над элементами коллекции целиком (добавь/удали/переставь) стандартными средствами не выражается — там либо JSON Patch-операции, либо отдельные саб-ресурсы со своими POST/DELETE.

## Главное правило: PATCH трогает только скаляры своего уровня

Тело PATCH отражает **только собственные скалярные поля ресурса** — то, что физически лежит в колонках его таблицы. Три запретные зоны:

- **Без id.** Идентификатор цели берётся из пути (`@PathVariable`), тело его не содержит. Обязательность обеспечивается тремя стражами: сам путь (без переменной маршрут не сматчится), валидация `@PathVariable`, поиск в сервисе → 404.
- **Без вложенных коллекций.** Коллекция в теле PATCH мгновенно размывает семантику: элемент без id — добавить? с id — обновить? отсутствующий в списке — удалить? Это уже PUT с полной заменой, притворяющийся PATCH.
- **Без ссылок на другие сущности.** Тот же размыв семантики в единственном числе.

Всё не-скалярное правится через саб-ресурсы своими глаголами:

| Что меняем | Как |
|---|---|
| Скаляры ребёнка | `PATCH .../exercises/{id}`, `PATCH .../repBlocks/{id}` |
| Добавить ребёнка | `POST` на коллекцию |
| Убрать ребёнка | `DELETE` на его адрес |

Контрольный вопрос при проектировании DTO: «это поле — колонка таблицы самого ресурса?» Да → включаем (nullable). Нет → выпиливаем: для этого будут отдельные роуты.

## Два стандартных формата тела

**JSON Merge Patch (RFC 7386)** — то, что принято в большинстве API. Тело — тот же JSON с частью полей; `null` означает «удалить поле». Для него модельруется DTO со всеми полями nullable: неприсланное и явный null в простейшем варианте не различаются — оба трактуются как «не трогать».

```json
PATCH /workouts/2/exercises/5
{ "exerciseName": "Жим узким хватом" }
```

**JSON Patch (RFC 6902)** — массив явных операций с путями (RFC 6901). Мощнее (есть add/remove/move/test), но требует парсера операций — в простых API избыщен.

```json
[
  { "op": "replace", "path": "/exerciseName", "value": "Жим узким хватом" }
]
```

В курсе — только Merge Patch-семантика.

## DTO для частичного обновления

```kotlin
data class WorkoutExercisePatchRequest(
    @field:[NotBlank Size(max = 100)]
    val exerciseName: String? = null,
    @field:Positive
    val orderIndex: Int? = null
)
```

- Все поля nullable: null = «клиент не прислал» = «не трогать».
- **Чего в DTO нет: ни id, ни вложенных DTO/коллекций** — только скаляры своего уровня (главное правило выше). Если рука тянется добавить в patch-DTO список детей или ссылку — стоп, для этого свой роут.
- Валидация над nullable-полями пропускает null (правило из урока 5) — присланное не null-значение валидируется как обычно.
- Крайний случай: пустой объект `{}` — юридически валиден, но бессмысленен. Если хочется отвергать — отдельная проверка «хотя бы одно поле не null» (ручная или через `@AssertTrue`-метод).

## Механика на сервере: в терминах жизненного цикла

1. Найти тренировку: тот же `findByIdWithExercises`, нет — 404. Managed с этого момента.
2. Найти упражнение **внутри коллекции тренировки**, не репозиторием: `workout.workoutExercises.find { it.id == exerciseId } ?: throw ExerciseNotFoundException(exerciseId)`. Поиск через коллекцию даёт инвариант «чужой id → 404 автоматически» — сущность другой тренировки в чужой коллекции не найдётся.
3. Применить только не null-поля:

```kotlin
request.exerciseName?.let { entity.exerciseName = it }
request.orderIndex?.let { entity.orderIndex = it }
```

4. `save` не нужен: сущность managed, flush по выходу из `@Transactional` сам найдёт изменения (dirty checking). Если ничего не поменялось — и UPDATE не будет.
5. Вернуть 200 + `WorkoutExerciseDto` свежего состояния.

## Почему PATCH дешевле PUT в запросов

Частичное обновление скаляров не трогает коллекции вовсе: ленивые `repBlocks` не инициализируются, пакетные запросы не нужны. Тело ответа собирается из уже загруженного. Типичный PATCH по саб-ресурсу — 2 SELECT (родитель с коллекцией) + 1 UPDATE.

## Ловушки

| Ловушка | Симптом | Приём |
|---|---|---|
| Неразличимость «не прислали» и «прислали null» | Невозможно очистить поле через PATCH | Для Merge Patch — принять (очистка отдельной операцией); если критично — `Optional`/JsonNullable на поле |
| Пустой патч `{}` | 200, ничего не изменилось | Допускается или 400 (проверка «хотя бы одно поле») |
| Поиск дочерней сущности репозиторием по id | PATCH по чужому id правит чужую сущность | Искать в коллекции родителя |
| PATCH поверх устаревших данных | Потерянное обновление при конкурентных правках | Оптимистичная блокировка: `@Version` (отдельная тема, на будущее) |
| PATCH целиком вложенной коллекции | Семантика размыта | Саб-ресурсы: POST/DELETE/PATCH по отдельным элементам |

## Почему путь через родителя

`PATCH /workouts/{workoutId}/exercises/{exerciseId}` — упражнение адресуется как саб-ресурс тренировки: путь отражает принадлежность. Плоский вариант `/exercises/{id}` тоже работает, но тогда проверку «упражнение принадлежит тренировке» сервер делать не может вовсе — принадлежность перестаёт быть частью адресации.
