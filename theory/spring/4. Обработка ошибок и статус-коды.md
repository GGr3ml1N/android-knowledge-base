## Модель: как исключение становится ответом

Цепочка при непойманном исключении:

1. Метод сервиса бросает исключение (например, `first {}` не нашел элемент → `NoSuchElementException`).
2. Исключение всплывает по стеку вызовов вверх: сервис → контроллер → DispatcherServlet.
3. DispatcherServlet не знает семантики исключения, ловит его на самом верху.
4. Отвечает BasicErrorController (появляется через auto-configuration ErrorMvcAutoConfiguration): статус 500, тело — общий JSON без деталей исключения.

```json
{"timestamp":"2026-11-03T14:00:31.022Z","status":500,"error":"Internal Server Error","path":"/workouts/99"}
```

- Текст исключения и стектрейс в ответ не попадают — сервер не показывает внутренности клиенту. Это инкапсуляция на границе с внешним миром.
- В ответе 500 «не найдено» и «база упала» неотличимы. Для HTTP это разные ситуации: 4xx = виноват клиент, 5xx = виноват сервер. Выбор статуса — часть контракта API.

Частые статусы и их смысл:

| Статус | Когда | Кто виноват |
|---|---|---|
| 400 Bad Request | Тело/параметры некорректны, не парсятся | Клиент |
| 404 Not Found | Ресурса с таким id нет | Клиент (запросил несуществующее) |
| 409 Conflict | Конфликт состояния (дубликат, параллельное изменение) | Клиент |
| 422 Unprocessable Entity | Синтаксически валидно, семантически нет (валидация бизнес-правил) | Клиент |
| 500 Internal Server Error | Неожиданный сбой | Сервер |

- Ошибки десериализации тела Jackson → `HttpMessageNotReadableException` → Spring по умолчанию переводит в 400. Пример: в `{"name": 123}` поле name не парсится в String → 400. Это честная семантика: клиент прислал мусор.

## @ControllerAdvice

- `@RestControllerAdvice` (Spring: `org.springframework.web.bind.annotation.RestControllerAdvice`) — обычный бин со стереотипной аннотацией, находится component scan'ом. Роль: перехват исключений из контроллеров.
- `@ExceptionHandler(T::class)` (Spring: `org.springframework.web.bind.annotation.ExceptionHandler`) на методе этого бина: метод вызывается, когда исключение типа T (или его подкласс) вылетает из любого контроллера.
- Параметр метода — само исключение. Возвращаемое значение сериализуется в тело ответа.
- Статус ответа задаётся либо `@ResponseStatus` на методе хендлера, либо через ProblemDetail (статус берётся из него).
- Подбор хендлера — по самому специфичному типу: есть хендлер на NoSuchElementException и на RuntimeException — для NoSuchElementException выберется первый. Ничего не подошло → BasicErrorController → 500.
- `@ExceptionHandler` можно ставить и внутри конкретного контроллера (локально), но тогда логика дублируется по контроллерам. Advice = один глобальный класс на всё приложение.
- try/catch в каждом методе vs advice: при 20 контроллерах — 20 копий обработки, плюс контроллер перестаёт быть тонким. Обработка ошибок — отдельный слой, как и логика.
- Где бросать: бизнес-исключения (не найдено, конфликт, нарушение правил) возникают в сервисе — слое, владеющем данными и правилами. Контроллер их не ловит и не оборачивает: исключение свободно всплывает через него в advice. Бросок в контроллере = контроллер начинает знать предметную область.

Пример скелета:

```kotlin
@RestControllerAdvice
class GlobalExceptionHandler {

    @ExceptionHandler(NoSuchElementException::class)
    fun handleNotFound(ex: NoSuchElementException): ProblemDetail =
        ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.message)
}
```

## ProblemDetail (RFC 7807)

- `org.springframework.http.ProblemDetail` — стандартизированное тело ошибки (RFC 7807), вместо самодельных `{"error": "что-то"}`.
- Поля: type (URI, идентифицирующий тип проблемы), title (короткое человекочитаемое название), status (HTTP-статус), detail (человекочитаемые детали конкретного случая), instance (URI, где произошла проблема).
- Создание: `ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, "Workout 99 not found")`. Дополнительные поля: `problem.setProperty("workoutId", 99)`.
- Content-Type ответа: `application/problem+json` — по нему клиент отличает стандартную ошибку от обычного DTO.
- Единый формат даёт: одинаковую обработку ошибок на клиенте для всех эндпоинтов, машиночитаемость, отсутствие договорённостей «у нас errors пишется так».

Пример тела:

```json
{
  "type": "about:blank",
  "title": "Workout not found",
  "status": 404,
  "detail": "Workout with id 99 not found",
  "instance": "/workouts/99"
}
```

## Успешные статусы

- По умолчанию любой успешный ответ — 200 OK, включая POST.
- `@ResponseStatus(HttpStatus.CREATED)` (Spring: `org.springframework.http.HttpStatus`) на методе контроллера → 201 при успехе. 201 = «ресурс создан», принято отвечать на POST, создающий ресурс. Тело при этом формируется возвращаемым значением как обычно.
- 204 No Content — успех без тела (типично для DELETE), применим позже.
- По конвенции на 201 добавляют заголовок Location со ссылкой на созданный ресурс (`/workouts/3`) — пока опционально.
- Полный контроль над тройкой «статус + заголовки + тело» даёт ResponseEntity (Spring: `org.springframework.http.ResponseEntity`):

```kotlin
@PostMapping
fun create(@RequestBody request: CreateWorkoutRequest): ResponseEntity<WorkoutDto> =
    ResponseEntity.status(HttpStatus.CREATED).body(service.create(request))
```

- ResponseEntity нужен, когда заголовки зависят от данных (Location, ETag, заголовки пагинации). Простые случаи — через @ResponseStatus.

## Ловушка широких исключений

- Глобальный хендлер на общий тип перехватывает ВСЕ исключения этого типа из любого места. NoSuchElementException возникает в двух разных ситуациях: «тренировка не найдена» (first) и «список пуст, last() нечего вернуть» (генерация id). Смыслы разные, тип один.
- После добавления хендлера на NoSuchElementException сбой генерации id в POST начнёт маскироваться под 404 «не найдено» — неверная семантика и скрытый баг.
- Решение — собственное исключение предметной области:

```kotlin
class WorkoutNotFoundException(id: Int) : RuntimeException("Workout with id $id not found")
```

- Сервис бросает WorkoutNotFoundException, хендлер ловит WorkoutNotFoundException. Общие типы JDK не перехватываются.
- Правило: хендлеры на предметные исключения; на общие типы (RuntimeException, Exception) — хендлер-последняя линия обороны с 500 и общим текстом, не с маскировкой под 4xx.

## Checked и unchecked: разница Kotlin и Java

- Java: Exception делится на checked (подклассы Exception, кроме RuntimeException — например IOException, SQLException) и unchecked (RuntimeException и подклассы). Checked обязаны быть пойманы или объявлены в throws — контроль на уровне компилятора.
- Kotlin: концепции checked нет. Компилятор не требует ловли никаких исключений, ключевого слова throws нет. Все исключения ведут себя как unchecked.
- Интероп с Java: kotlin-функция без аннотации @Throws в байткоде не объявляет checked-исключения → Java-коллеры не обязаны ловить, даже если исключение наследует IOException. @Throws(IOException::class) добавляет throws в сигнатуру — тогда Java-компилятор потребует обработку.
- Выбор базового класса в Kotlin — RuntimeException, несмотря на отсутствие разницы для компилятора:
  - семантика: явное заявление «обрабатывать не обязаны», наследование от Exception — визуальный намёк на checked, которого в Kotlin нет;
  - конвенция Spring: вся иерархия исключений фреймворка — RuntimeException; checked-исключения JDBC (SQLException) оборачиваются в unchecked DataAccessException;
  - устойчивость к Java-интеропу: исключение остаётся unchecked даже с @Throws.
- Позиция Spring по checked-исключениям принципиальная: они не компонуются с лямбдами и стримами, порождают шаблонный try/catch и throws через все слои. В приложении на Spring — только unchecked.
- Наследование от Exception имеет смысл только при сознательном проектировании API для Java-потребителей с обязательной обработкой.
