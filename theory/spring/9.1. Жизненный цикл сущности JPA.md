## Persistence context

- Рядом с каждой транзакцией живёт **persistence context** (кэш первого уровня). В JPA это интерфейс `jakarta.persistence.EntityManager`, реализация Hibernate — `org.hibernate.Session`.
- Spring подсовывает не настоящий EntityManager, а прокси, привязанный к текущей транзакции. Все вызовы репозиториев внутри одного `@Transactional`-метода попадают в один контекст; при выходе из метода контекст закрывается.
- Вне транзакции для веб-запроса контекст всё равно открыт (open-in-view по умолчанию), но рассчитывать на это в сервисной логике не стоит.
- Контекст хранит все загруженные сущности + снапшот их состояния на момент загрузки. Проверить, под управлением ли объект: `entityManager.contains(entity)`.

## Четыре состояния сущности

| Состояние | Признак | Изменения отслеживаются? |
|---|---|---|
| **Transient** (новая) | Не загружалась из БД, `persist()` не вызывался, id = дефолт | Нет |
| **Managed** (под управлением) | Лежит в контексте: загружена запросом либо присоединена через `persist()`/`merge()` | Да (dirty checking) |
| **Detached** (отсоединённая) | Контекст закрылся (commit / выход из `@Transactional`), объект жив | Нет |
| **Removed** (удалённая) | Вызван `remove()` | Удалится на flush |

Переходы:

```text
transient --загрузка из БД / persist()-->  managed
managed   --commit, закрытие сессии----->  detached
detached  --merge()--------------------->  managed (возвращается managed-копия)
managed   --remove()-------------------->  removed  (DELETE на flush)
managed   --убрать из коллекции--------->  removed  (orphanRemoval)
```

## Как сущность становится managed

- загрузка через `find*`-методы или JPQL-запрос внутри транзакции;
- `EntityManager.persist(entity)` — transient → managed;
- возвращаемое значение `EntityManager.merge(entity)` — важно: merge не «присоединяет» переданный объект, а переносит состояние на managed-копию и возвращает её;
- каскад от managed-родителя (`CascadeType.ALL`/`PERSIST` и т.п.).

## Что даёт managed

1. **Dirty checking.** Hibernate сравнивает текущее состояние со снапшотом на flush и сам шлёт `UPDATE` за расхождения. Никаких вызовов не требуется — достаточно присваивания полей.
2. **Каскады срабатывают сами.** Вставка нового ребёнка в managed-коллекцию → `INSERT` на flush без всякого `save` у ребёнка.
3. **Гарантия идентичности.** В пределах контекста все загрузки по одному id возвращают один и тот же Java-объект: `find(id) == find(id)`.

## Когда происходит flush

- коммит транзакции;
- явный `EntityManager.flush()`;
- перед запросом, затрагивающим уже изменённые таблицы (режим AUTO).

До flush в БД ничего не уходит, хотя сущность уже managed и изменения «внутри» неё сделаны.

## save() в терминах жизненного цикла

`org.springframework.data.jpa.repository.support.SimpleJpaRepository`:

```java
@Transactional
public <S extends T> S save(S entity) {
    if (entityInformation.isNew(entity)) {
        em.persist(entity);      // transient -> managed
        return entity;
    } else {
        return em.merge(entity); // detached: слияние с managed-копией
    }
}
```

Порядок определения «новой»:
1. реализован `org.springframework.data.domain.Persistable.isNew()` — берётся оно;
2. иначе есть поле `@Version` — новая, когда version == null;
3. иначе — по id: `id == null` → новая.

Тонкость с `var id: Long = 0`: id никогда не null, правило 3 даёт всегда `false`, и save идёт в merge-ветку. На transient-объекте merge с несуществующим id ничего не находит, копирует состояние на свежую managed-копию, и на flush она вставляется — POST работает, но через лишний SELECT на каждую сущность. Проверяется по логу `show-sql`: если перед INSERT'ами есть SELECT — это merge-ветка. Честный persist требует `id: Long? = null` либо `@Version`, либо `Persistable`.

Отсюда правило: save нужен только, чтобы присоединить transient- или detached-объект. Переданная managed-сущность ничем не станет — save над ней no-op.

## Отдельно про GenerationType.IDENTITY

`persist` с IDENTITY выполняет INSERT немедленно — ключ нужен до commit, БД выдаёт его при вставке. Поэтому после save у новой сущности сразу заполнен id. Обратная сторона: JDBC-батчинг вставок с IDENTITY невозможен, на больших объёмах взрослые схемы переходят на SEQUENCE.

## Detached на практике

- Все GET-методы сервиса возвращают DTO внутри `@Transactional`, пока граф managed и коллекции инициализированы; за пределами транзакции DTO — обычные данные, проблем нет.
- Попытка дотянуться до lazy-коллекции detached-сущности → `LazyInitializationException` (маскируется open-in-view в веб-запросах, поэтому смотреть «голое» поведение удобно в тестах/CLI).
- Изменения detached-сущности молча теряются: снапшота нет, dirty checking не работает. Чтобы дотянуть до БД, объект нужно вернуть в контекст через merge.

## Пример: эволюция состояний в сервисе

```kotlin
@Transactional
fun addWorkout(request: WorkoutRequest): WorkoutDto {
    val entity = request.toEntity()     // transient: контекст о нём не знает
    // присваивания полей здесь никуда не попадут
    val saved = workoutRepository.save(entity) // transient -> managed (persist или merge)
    saved.id                            // с IDENTITY уже заполнен БД
    return saved.toDto()                // коллекции инициализированы — мапим спокойно
}                                       // commit: flush; дальше saved — detached

@Transactional
fun updateWorkout(id: Long, request: WorkoutRequest): WorkoutDto {
    val workout = workoutRepository.findByIdWithExercises(id)
        ?: throw WorkoutNotFoundException(id) // managed с этой строки
    workout.name = request.name               // снапшот расходится — увидит flush
    workout.syncExercises(request.workoutExercises) // дифф коллекций тоже отслеживается
    // save не нужен: объект уже managed
    return getWorkoutById(id)
}   // commit: UPDATE родителя, INSERT/DELETE детей по диффу; workout — detached
```

## Ловушки

| Ошибка | Симптом |
|---|---|
| Менять detached-сущность и ждать UPDATE | Изменения молча теряются |
| `save` над managed-сущностью | Лишний шум, фактический no-op |
| Использовать результат `merge` не до конца понимая: переданный объект не становится managed | Изменения «потерянного» объекта не попадают в БД |
| Дергать lazy-поля detached | `LazyInitializationException` |
| Считать, что managed = «уже в БД» | До flush записи нет; IDENTITY — исключение по id |
